# DECISIONS.md — Journal des décisions

Format : `[Date] Décision — Raison — Alternatives écartées`

- **Fournisseur de paiement MVP : FedaPay** — l'IFU professionnel a été obtenu, éligibilité confirmée pour ce statut. Kkiapay écarté pour le MVP faute de RCCM (nécessaire pour un compte marchand actif au Bénin côté Kkiapay). Architecture `PaymentService` maintenue abstraite pour ajouter Kkiapay plus tard sans réécrire le produit.
- **Prix unique 1 000 FCFA, sans abonnement** — pour tester une hypothèse de valeur simple avant toute complexité de facturation récurrente.
- **Calculs financiers hors IA** — fiabilité et prévisibilité des chiffres affichés jugées non négociables ; l'IA reste cantonnée à la compréhension, la suggestion et l'explication.
- **Stack : Next.js + NestJS + PostgreSQL** — cohérent avec les compétences déjà en place et les besoins du MVP (pas de sur-ingénierie).
- **ORM : Prisma** — retenu pour la base de données PostgreSQL (migrations via Prisma Migrate, schéma dans `schema.prisma` comme source de vérité). TypeORM écarté.
- **Couleur de marque : vert émeraude (`emerald-500 #059669`)**, dégradé avec le cyan — le violet initialement proposé a été écarté. Distinct du vert sémantique `success` (voir `design/COLORS.md`).

- **[2026-09-19] Structure du dépôt : monorepo pnpm workspaces** (`apps/web`, `apps/api`), équipe solo au MVP, partage futur de types entre front/back, déploiement coordonné plus simple. Repos séparés écartés : se justifieraient avec une équipe aux accès/pipelines distincts, pas le cas ici.
- **[2026-09-19] Prisma épinglé en 7.10.0 (pas `latest`)**, le tag npm `latest` de `prisma` pointe vers une release candidate (`8.0.0-rc.x`) au moment du bootstrap ; 7.10.0 est la dernière version stable (tag `prev`). À remonter en 8.x quand cette version sera stabilisée, avec une entrée dédiée.
- **[2026-09-19] Vert de marque intensifié : `emerald-500 #008558`** (au lieu de `#059669`), demande explicite d'un vert plus intense. Saturation poussée à 100% (au lieu de ~94%) à luminosité légèrement réduite plutôt qu'un vert plus clair, pour préserver le contraste du texte blanc sur les CTA (`#059669` donnait déjà un ratio marginal de 3.77:1 sur blanc ; `#008558` remonte à 4.67:1, conforme AA texte courant). `emerald-600` recalculé en cohérence (`#00693F`). `design/COLORS.md` mis à jour.
- **[2026-09-19] Moteur financier : montants en devise choisie par l'utilisateur, pas seulement FCFA.** Champ `currency` ajouté aux hypothèses (`XOF`, `EUR`, `USD`, `GBP`, `NGN`, `GHS` pour le MVP), demande explicite. Ne touche pas au prix fixe de l'analyse (1 000 FCFA, règle non négociable de `CLAUDE.md`) : il s'agit uniquement de la devise dans laquelle l'utilisateur exprime les chiffres de *son* idée. Tous les montants restent des entiers dans la plus petite unité de la devise (centimes pour EUR/USD/GBP/NGN/GHS, unité entière pour XOF), aucune conversion de change effectuée, le moteur ne fait que faire transiter l'étiquette de devise à travers le calcul. Aucune dépendance de calcul décimal ajoutée.

- **[2026-09-19] Postgres local (Docker Compose) exposé sur le port hôte 5433** (au lieu de 5432 prévu au plan Phase 3), le 5432 était déjà occupé localement. Le conteneur écoute toujours en 5432 en interne ; seul le mapping hôte et `DATABASE_URL` (`apps/api/.env.example`) changent. Aucun impact en dehors de l'environnement local.

- **[2026-09-19] Fournisseur IA (Phase 4) : Google Gemini (famille Flash), SDK officiel `@google/genai`.** Choisi pour son mode structured output natif (`responseSchema`), qui force une réponse JSON conforme à un schéma et réduit le risque d'extraction mal formée par rapport à un parsing de texte libre. Free-tier généreux (`docs/AI_ENGINE.md` : « privilégier une API économique / free-tier »). Groq écarté : modèles open-source moins fiables pour du JSON strict sans validation additionnelle. Modèle exact configurable via `GEMINI_MODEL` (défaut `gemini-2.5-flash`), pour pouvoir suivre les mises à jour de la famille Flash sans redéploiement de code.

- **[2026-09-20] Extraction du moteur financier en package partagé du monorepo (`packages/financial-engine`).** Nécessaire pour que la Phase 5b (module "Et si ?"/scénarios) recalcule côté navigateur sans aller-retour réseau à chaque interaction (connexions parfois lentes en Afrique de l'Ouest, `design/UX_PRINCIPLES.md`). Le package est consommé via un build `tsc` standard (`tsc -p tsconfig.build.json`, même mécanisme que `apps/api`), pas de step de build exotique. `apps/api/src/financial-engine/financial-engine.service.ts` reste le seul point d'entrée NestJS, désormais un fin wrapper délégant au package.
- **[2026-09-20] Projection annuelle avec saisonnalité : 4 profils prédéfinis, pas de saisie manuelle mois par mois.** Un porteur de projet pas encore lancé n'a pas de vraies données mensuelles ; les profils (`stable`, `fetes_fin_annee`, `ete`, `rentree_scolaire`) sont des points de départ à calibrer avec des données réelles avant mise en production, même statut d'incertitude assumée que `SCENARIO_DELTAS` (Phase 2). La saisonnalité n'affecte que le volume (jamais prix/coûts), via le même mécanisme `applyDelta` que les scénarios existants — composable avec eux, pas exclusif.
- **[2026-09-20] Librairie de graphiques : Recharts (Phase 5b).** Composants React déclaratifs, bon support tooltips/responsive, facile à styler avec les tokens CSS existants (`design/COLORS.md`). `apps/web` importe aussi directement le package `financial-engine` (Phase 5a) pour recalculer côté navigateur sans aller-retour réseau à chaque interaction des écrans "Et si ?"/"Scénarios" — contrairement à `BusinessModel`/`CurrencyCode` (redéfinis localement depuis la Phase 3 car couplés à `@prisma/client`), `financial-engine` est un package pur conçu pour être partagé tel quel entre `apps/api` et `apps/web`.

- **[2026-09-20] Élargissement conscient du périmètre MVP : le "rapport final" (déjà prévu, `docs/MVP_SCOPE.md`) sera enrichi en business model canvas complet (9 blocs Osterwalder), avec recommandations sur le capital déjà disponible vs. le besoin financier estimé.** Demande explicite de l'utilisateur, choix confirmé pour le canvas complet plutôt qu'une version simplifiée après avoir vu le coût réel (5-7 blocs qualitatifs sans équivalent dans les données déjà collectées). Entre en tension avec l'exclusion MVP initiale « pas de génération de business plans interminables » — arbitrage : le canvas reste *un document structuré à forme fixe* (9 blocs prédéfinis, jamais de contenu libre illimité), rempli pour 2 blocs par calcul déterministe (structure de coûts, flux de revenus — jamais stockés comme texte, calculés à la volée par `financial-engine`) et pour 7 blocs par une suggestion IA que l'utilisateur valide/édite (même pattern que la Phase 4), ce qui garde l'esprit de l'exclusion (pas de génération ouverte et non maîtrisée). Le plan de lancement détaillé post-analyse ("comment te lancer si ça tient") est explicitement écarté de cette itération et reporté en V2. Toute donnée chiffrée affichée dans ce rapport reste soumise à la règle `CLAUDE.md` #3 (calculs déterministes, jamais produits par l'IA) : le "besoin financier" est un calcul (capital nécessaire − capital déclaré par l'utilisateur), pas une estimation générée par un modèle. Découpé en deux sous-phases (comme 5a/5b) : Phase 6a = capture des 7 blocs qualitatifs manquants ; Phase 6b = écran capital + offre + paiement (TestProvider en développement, FedaPay réel différé) + rendu du rapport complet.
- **[2026-09-20] Dashboard admin (accès aux données utilisateurs collectées) : reconnu comme besoin réel mais explicitement séquencé après le rapport final enrichi.** Nouvelle brique hors MVP tel que documenté (aucune mention dans `docs/MVP_SCOPE.md`), touche à l'authentification et à l'accès à des données potentiellement sensibles — traitée comme un sujet de brainstorm à part entière, pas ajoutée au flux utilisateur en cours.
